## Обзор

Периферийные (edge) и облачные вычисления в контексте систем ОВК представляют собой гибридный подход к обработке данных и управлению, при котором часть логики исполняется локально на граничных устройствах, а часть — на удалённых серверах. Fog-computing (туманные вычисления) занимает промежуточное положение между сенсорами/актуаторами и облачными центрами обработки данных, позволяя снизить задержку (latency), уменьшить объём передаваемых данных и повысить надёжность системы при сбое сетевого соединения.

В современных системах вентиляции, кондиционирования и теплоснабжения необходимо обрабатывать в реальном времени десятки или сотни параметров (температура, влажность, давление, скорость воздуха, качество воздуха, энергопотребление), координировать работу множества приводов и датчиков, оптимизировать энергоэффективность. Облачные платформы предоставляют масштабируемость и долгосрочное хранилище данных для аналитики; периферийные узлы обеспечивают быстрый локальный отклик и функционирование при потере соединения с интернетом.

## Физические принципы и архитектура

Модель распределённых вычислений в ОВК основана на иерархии обработки информации:

$$\text{Датчик} \to \text{Edge-устройство} \to \text{Fog-узел} \to \text{Облако}$$

Каждый уровень имеет различные требования к вычислительной мощности, задержке и надёжности. Edge-устройства (микроконтроллеры, промышленные ПК) выполняют критичные по времени функции: регуляция температуры по локальному датчику, защита от перегрева, аварийное отключение. Fog-узлы координируют несколько edge-устройств, выполняют аналитику и принимают решения на уровне здания или участка сети. Облачные сервисы аккумулируют историческую информацию, проводят глубокую аналитику, оптимизируют расписания и предиктивное обслуживание.

Критическая метрика — времю отклика (response time):
$$t_{\text{отклика}} = t_{\text{акв}} + t_{\text{обр}} + t_{\text{сети}} + t_{\text{испол}}$$

где $t_{\text{акв}}$ — время сканирования датчиков, $t_{\text{обр}}$ — обработка, $t_{\text{сети}}$ — передача по сети, $t_{\text{испол}}$ — исполнение команды. Для жизнебезопасных функций (например, автоматическое отключение при обнаружении избыточного давления) общее время не должно превышать 50–500 мс в зависимости от норматива.

## Компоненты и архитектура

### Локальная обработка данных на edge-устройствах

Edge-вычислители расположены непосредственно у источников данных (воздухозаборник, помещение, котельная). Типичные компоненты:

- **Микроконтроллеры / однoплатные компьютеры**: Arduino, Raspberry Pi, промышленные ПЛК (Siemens S7-1200, Allen-Bradley Micro800). Мощность обработки: 100 МГц – 2 ГГц.
- **Датчики (Input)**: температура (Pt100, NTC, цифровые DS18B20), влажность (ёмкостные, резистивные), давление (0–10 кПа, 0–2,5 кПа), качество воздуха (CO₂, PM2.5, VOC).
- **Приводы (Output)**: электромагнитные клапаны, частотные преобразователи для вентиляторов, нагревательные элементы.

Локальная логика управления работает по заранее программируемым алгоритмам (PID-регуляторы, гистерезис, таблицы). Пример ПИД-регулятора для расхода воздуха:

$$u(t) = K_p e(t) + K_i \int_0^t e(\tau) d\tau + K_d \frac{de}{dt}$$

где $e(t) = T_{\text{зад}} - T_{\text{факт}}$ — ошибка, $K_p, K_i, K_d$ — коэффициенты настройки.

### Управление с минимальной задержкой

Периферийные узлы должны реагировать на события с задержкой **не более 100–500 мс** (в зависимости от критичности). Достигается:

- **Детерминированное время исполнения**: hard real-time ОС (VxWorks, QNX, RTLinux) или встроенное ПО без многозадачности.
- **Локальное хранилище параметров**: регистр конфигурации, таблицы уставок (setpoints) хранятся в энергонезависимой памяти (Flash, EEPROM).
- **Минимизация сетевых запросов**: периферия не ждёт ответа облака для выполнения аварийных действий.

### Распределённый интеллект и локальная аналитика

На уровне fog-узлов (локальный шлюз, промышленный компьютер в машинном отделении):

- Агрегация данных от 10–100 edge-устройств.
- Статистическая обработка: скользящее среднее (moving average), расчёт вариации параметров.
- Предварительная фильтрация аномалий (outliers).
- Локальная оптимизация: например, балансировка нагрузки между двумя котлами на основе текущего расхода горячей воды без задержки облачного запроса.

Типичный объём данных на fog-узле: 10–100 параметров, частота сканирования 1–10 Гц, недельное локальное хранилище — ~10 ГБ.

### Аналитика на периферии в реальном времени

Machine learning модели малого размера развёртываются на edge и fog устройствах. Примеры:

- **Обнаружение аномалий**: изолировать лесная (Isolation Forest), случайные леса для классификации режимов работы.
- **Предиктивное обслуживание**: прогнозирование отказа фильтра на основе дифференциального давления и времени наработки.
- **Оптимизация в реальном времени**: алгоритм выбора оптимальной температуры подачи на основе внешней температуры и занятости помещений.

Размер моделей: 1–50 МБ, инференс на CPU за 10–100 мс.

### Архитектура узлов fog-вычислений

Типовой fog-узел включает:

| Компонент | Описание | Пример |
|-----------|---------|--------|
| **Сетевой интерфейс** | Модемы, маршрутизаторы, WiFi, LTE, 5G | Industrial IoT gateway |
| **Локальное хранилище** | База данных, кэш, буфер событий | PostgreSQL, InfluxDB |
| **Контейнеризация** | Docker, микросервисы | Edge Runtime (Azure IoT Edge) |
| **Обработка данных** | Потоковая аналитика | Apache Kafka, MQTT broker |
| **Безопасность** | VPN, TLS, аутентификация | mTLS, сертификаты X.509 |

### Координация периферии и облака

Двусторонний обмен:

- **Периферия → Облако**: передача телеметрии (T, P, расход, события) по расписанию или при изменении, буферизация при потере соединения.
- **Облако → Периферия**: обновление конфигурации, расписание отопления, новые модели, команды диагностики.

Протоколы: **MQTT** (QoS 0/1), **HTTP REST**, **CoAP**. Частота синхронизации: от 5 минут до 1 часа для некритичных параметров.

## Методы расчёта и проектирования

### Требования к вычислительной мощности

Для edge-узла управления вентиляционной установкой:

- Частота опроса датчиков: $f_{\text{сканир}} = 10$ Гц
- Число параметров: $N = 20$ (температура, влажность, давление по 5–6 точкам)
- Объём данных в секунду: $V = N \cdot 4 \text{ байта} \cdot f = 20 \cdot 4 \cdot 10 = 800 \text{ байт/с}$
- За сутки: $V_{\text{сут}} = 800 \cdot 86400 = 69,12 \text{ МБ}$ (при прямой записи; с сжатием — 10–20 МБ)

Вычислительная нагрузка: ПИД-регулятор, фильтр Калмана требуют ~1000 операций на итерацию, итого ~200 кОП/с — посильно для MCU с частотой 100 МГц.

### Размер буфера данных

При перебое соединения с облаком периферийный узел должен хранить телеметрию локально:

$$B = V_{\text{сут}} \cdot t_{\text{отказа}}$$

где $t_{\text{отказа}}$ — ожидаемая длительность потери соединения. Для систем ОВК: 6–24 часа.

$$B = 20 \text{ МБ/сут} \cdot 1 \text{ сут} = 20 \text{ МБ} \quad \Rightarrow \quad \text{SD-карта 32 ГБ достаточна на годы}$$

## Применение в ОВК

### Сценарии использования

1. **Многозональная система VAV (Variable Air Volume)**
   - Edge-контроллеры в каждой зоне (в коробке VAV-терминала) управляют клапаном и датчиком температуры с задержкой <100 мс.
   - Fog-узел в центральной установке координирует давление в воздуховоде, расход свежего воздуха, ограничения по энергии.
   - Облако проводит оптимизацию расписания на неделю на основе прогноза погоды и занятости.

2. **Система отопления с несколькими котлами**
   - Каждый котел имеет локальный PLC (Siemens S7-1200) с ПИД-регулятором температуры подачи.
   - Fog-шлюз (промышленный PC с 2–4 ядрами) балансирует нагрузку, переключает котлы, ведёт статистику энергопотребления.
   - Облако предсказывает требуемый график на основе метеоданных и истории потребления.

3. **Качество воздуха в офисном зданииq**
   - Датчики CO₂ и PM2.5 в каждом помещении (IoT-сенсоры).
   - Edge-обработка: локальное управление рециркуляцией и фильтрацией при превышении пороговой концентрации.
   - Fog-аналитика: обнаружение утечек, прогноз требуемого воздухообмена.
   - Облако: мониторинг соответствия СП 60.13330 (норма — не менее 30 м³/ч на человека; CO₂ < 800 ppm).

### Климатические зоны и требования

| Зона (ASHRAE) | Стратегия | Критические параметры |
|---------------|-----------|----------------------|
| **Холодная** (< −20 °C) | Предотвращение замерзания, рекуперация | Температура воды в трубах > 5 °C |
| **Умеренная** | Сезонная оптимизация, баланс отопление/охлаждение | Dew point, избыточная влажность |
| **Жаркая влажная** | Осушение, обводной воздух, шумоподавление | Абсолютная влажность |

## Стандарты и нормативы

- **ASHRAE 90.1** (HVAC Energy Code) — требования к энергоэффективности, включая управление, мониторинг.
- **ASHRAE 189.1** / **LEED v4** — высокоэффективные здания, роль автоматизации.
- **EN 13779** (воздухообмен в зданиях) — категории вентиляции, требования к контролю качества.
- **ISO 16484-3** (BACnet) — стандартный протокол для систем управления зданиями (BMS).
- **ISO/IEC 27001** — безопасность IoT-систем в критичной инфраструктуре.
- **СП 60.13330** (актуализация СНиП 41-01-2003) — норма воздухообмена, требования к системам вентиляции в России.
- **ГОСТ Р 56408** — энергосбережение в зданиях, мониторинг энергопотребления.

## Практические рекомендации

### Типовые диапазоны и значения по умолчанию

| Параметр | Значение | Примечание |
|----------|----------|-----------|
| Время отклика edge | 50–500 мс | Критичные функции < 100 мс |
| Частота передачи в облако | 5–60 минут | В зависимости от стабильности сети |
| Локальное хранилище | 7–30 дней | Для работы при потере интернета |
| Инференс ML-модели | 10–100 мс | На CPU без GPU |
| Размер моделей | 1–50 МБ | Помещаются в RAM edge-устройства |

### Частые ошибки

1. **Избыточная передача в облако** — отправка всех 100+ параметров каждые 5 секунд перегружает сеть и облако. Решение: агрегация, отправка изменений (delta encoding), сжатие.
2. **Отсутствие локального буфера** — при отказе интернета система теряет управление. Всегда реализуйте локальное хранилище на 6–24 часа.
3. **Недостаточная латентность edge-логики** — облачные API для каждого цикла управления (например, вызов для PID-регулятора). Правило: всё критичное по времени — на периферии.
4. **Игнорирование безопасности** — fog-узлы часто подключены к сети. Требуется двусторонняя аутентификация (mTLS), шифрование (TLS 1.2+), обновления ПО.

### Рекомендуемая архитектура для новых проектов

```
Помещение (датчики) 
  ↓ (Modbus, 4–20 мА)
Edge-контроллер (PLC, 10–50 мс отклик, локальные алгоритмы)
  ↓ (Ethernet, MQTT с QoS 1)
Fog-шлюз (промышленный ПК, агрегация, статистика)
  ↓ (Secured REST API, TLS 1.3, токены JWT)
Облако (Azure IoT Hub, AWS IoT Core, Google Cloud IoT)
  ↓
Аналитика, ML, веб-интерфейс, исторические отчёты
```

Использование контейнеров (Docker) на fog-узлах позволяет быстро развёртывать обновления алгоритмов, не прерывая локальное управление. Рекомендуется двусторонняя синхронизация: облако отправляет новые конфигурации, периферия — события и метрики высокого уровня.
